# JPO Huddle

A top-down multiplayer virtual office (a Phaser 3 game) for the JustPressOne team: people walk around as pixel avatars, chat, earn coins, buy cosmetics, and read the announcement board. All game state is now durable in Postgres.

## Run & Operate

- `pnpm --filter @workspace/jpo-huddle run dev` — run the JPO Huddle game server (`node server.js`)
- `pnpm --filter @workspace/api-server run dev` — run the API server (port 5000)
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm run build` — typecheck + build all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec
- `pnpm --filter @workspace/db run push` — push DB schema changes (dev only)
- `pnpm --filter @workspace/jpo-huddle run loadtest -- --n 100 --duration 60` — load-test the game server with N headless players (see `artifacts/jpo-huddle/loadtest/README.md`; verdict from the last full run: `loadtest/RESULTS.md` — PASS at 100 players)
- Required env: `DATABASE_URL` — Postgres connection string; `ADMIN_PASSWORD` — gates the in-game admin panel; `SESSION_SECRET` — signs the resume tokens that auto-rejoin returning players (when unset, auto-rejoin is disabled and everyone uses the normal register flow)

## Stack

- pnpm workspaces, Node.js 24, TypeScript 5.9
- API: Express 5
- DB: PostgreSQL + Drizzle ORM
- Validation: Zod (`zod/v4`), `drizzle-zod`
- API codegen: Orval (from OpenAPI spec)
- Build: esbuild (CJS bundle)

## Where things live

- `artifacts/jpo-huddle/server.js` — the whole game server: Express 5 static serving (with cache-busting `BUILD_STAMP`), socket.io event handlers, and all DB reads/writes via a raw `pg` Pool. Plain ES modules, run with `node server.js` (no build step).
- `artifacts/jpo-huddle/public/index.html` — the entire client (~2100 lines of plain JS): Phaser 3 + socket.io loaded from CDN, no bundler. Source of truth for socket event shapes and the `CLOTH_COLORS` palette.
- `artifacts/jpo-huddle/public/assets/Office.tmj` — the Tiled map (Floor/Furniture/Wall layers). Source of truth for room layout, furniture placement, and walkable paths.
- `lib/db/src/schema/jpoPlayers.ts`, `lib/db/src/schema/jpoAnnouncements.ts` — Drizzle table definitions (source of truth for the DB schema). Re-exported from `lib/db/src/schema/index.ts`. These exist so `drizzle-kit push` and future migrations work; the game server itself talks to Postgres with raw SQL, not Drizzle.

## Architecture decisions

- **DB is the source of truth; the in-memory maps (`players`, `pending`, `admins`) are only a live-connection cache.** Every durable field (coins, cosmetics, approval, announcer status, position, announcements) is read from / written to Postgres.
- **`server.js` uses a raw `pg` Pool, not the Drizzle client.** This keeps the server as plain `node server.js` (no `tsx`/transpile step) while still using the shared `@workspace/db` schema for `push` and future publish-time migrations.
- **Identity key = lowercased email.** `jpo_players.email` is the primary key. Registering an already-approved email auto-restores the player straight into the office (no re-approval). `restorePlayer()` is the single seam for this; the identity gate that decides *who* may restore lives in the `register` handler.
- **Kick = revoke.** Because an approved email auto-restores on next connect, kicking flips `approved` back to `false` (a session-only removal would just let them walk right back in).
- **Coin/position writes are batched to the once-per-minute coin tick** (and a final flush on disconnect), so per-move traffic never hits the DB. Coin awards and purchases use atomic relative SQL (`coins = coins + N ... RETURNING`) so concurrent ticks and buys can't race.
- **One live session per email:** a new connection for an email already online disconnects the older socket (`dropLiveByEmail`).

## Gotchas

Grouped by area. Every entry documents a place where two independent pieces of code (client/server, or two server paths) must be kept in lockstep, plus the accepted tradeoffs baked into the design.

### Networking & socket safety

- **Never destructure raw socket payloads in the handler parameter list.** `socket.on("evt", ({ x } = {}) => …)` still throws on an explicit `null` payload — one malicious `emit("evt", null)` crashes the whole server (this was a live DoS until fixed). Every handler takes `(payload)` and destructures from `payload || {}`; keep this pattern for all new socket events.
- **Whisper targets are socket ids, not names.** The DM composer's autocomplete binds `_dmTargetId` to a specific live session (the client `_online` roster mirrors `_addOtherPlayer`'s self/stale-ghost skip rule), so display-name collisions can't misroute a whisper; ambiguous typed names are rejected with a "pick one" error rather than guessed. Server-side, `whisper` shares the sender's `chatBucket` with public chat and delivers via `io.to(targetId)` only — grace-window (briefly disconnected) targets get the friendly "not in the office" error by design. Chat and the DM composer are mutually exclusive (each opener closes/guards against the other, plus owner/board panels and the shop modal).
- **The chat history log panel is PASSIVE and client-only by design** (user explicitly declined persistence — no server/DB involvement at all). It has no input field, so it deliberately does NOT join the `chatting` mutual-exclusion seams and never blocks movement or other panels. It feeds off an ADDITIONAL DOM-level `socket.on('chatMessage')` listener (socket.io multi-listener, same pattern as the `_online` roster) — the Phaser scene's bubble handler is untouched — plus one-line `_chatLogAdd` hooks inside the existing `whisper`/`whisperSent` handlers. Entries are built with `textContent` only (never innerHTML), capped at `CHATLOG_MAX` (200) DOM nodes, and auto-scroll only when already at the bottom (measured BEFORE append). The C-key toggle guards on `body.playing` + no INPUT/TEXTAREA focus + no modifier keys; its Esc-close is guarded behind every other panel/modal flag so those keep first claim on Esc.
- **Display name ≠ full name.** `rowToPlayerState` sets `name = nickname || first_name || name` (what nametags/chat/announcements show) and keeps `fullName` for the admin panel (`_playerList` sends both; `_pendingList` sends full name + nickname). Announcements snapshot the author's display name at post time — an accepted tradeoff, old posts keep the old name.
- **Empty-email clients fall back to session-only play** (nothing persists) because email is the PK. The web client always requires a valid email, so this only affects non-standard clients.

### Auth & sessions

- **Password auth with a legacy-claim (TOFU) rule.** Accounts have a scrypt password hash (`scrypt:<salt>:<hash>`, hashed async so the event loop never blocks). A row with `password_hash IS NULL` is a legacy passwordless account: the FIRST register with that email claims it by setting a password, atomically (`UPDATE … WHERE password_hash IS NULL RETURNING` — a lost race falls back to verifying against the winner's hash). Same trust level as the old email-only model at claim time, but locked after that. Order matters in `register`/`login`: password verification happens BEFORE any profile mutation or `dropLiveByEmail` so a wrong password can't overwrite a profile or disconnect the real player. Per-EMAIL limiter (5 attempts/30s, module-level `authAttempts`) is checked BEFORE any scrypt call so a flood can't exhaust the libuv threadpool; note it counts SUCCESSFUL auths too, so 5 rapid sign-ins for one email briefly lock it — not a bug. Plaintext password over socket.io is fine — WSS terminates TLS at the proxy.
- **The pending queue is DB-backed; `dismissed` decides who shows.** `_pendingList()` (async) merges live in-memory `pending` sockets with DB rows `approved = false AND dismissed = false`; offline rows get id `email:<email>` + `offline: true`, and `approvePlayer`/`rejectPlayer` resolve that id back to the row (approve also falls back to ANY live pending socket for the email, since the person may have reconnected under a new socket id). Reject and kick set `dismissed = true` (otherwise every rejected person would sit in the queue forever); ANY active return — register upsert, sign-in pending branch, resume pending branch — clears it, restoring the old "connected = queued" semantics. Session-only (no-email) registrants remain memory-only by design. Belt-and-braces freshness: the client polls `adminRefresh` every 10s while the panel is open. The `dismissed` column is added by an idempotent `ALTER TABLE … IF NOT EXISTS` at server boot so a production DB that predates it self-heals on publish; legacy unapproved rows (old rejects/kicks from before the column) resurface ONCE and need a one-time ✗ dismissal. SECURITY seam: because `email:<address>` ids are embedded in the panel's inline `onclick='…'` attributes, the client `esc()` MUST escape single quotes (it does) and `register` enforces a strict `EMAIL_RE` shape server-side (quotes/spaces/HTML can never become a PK) — keep both when touching either.
- **Admin status must be re-asserted on every socket reconnect.** The server's `admins` set is per-socket-id and in-memory, so a blip or restart silently drops it (pushes stop, panel goes stale). The client keeps the confirmed-good admin code in a memory-only variable (`_adminPwd`, never persisted) and an additional `connect` listener re-emits `adminAuth`; `adminAuthOk` distinguishes manual unlock (pwd modal open → opens the panel) from silent re-auth (flags only). A failed SILENT re-auth (rotated `ADMIN_PASSWORD`) resets `_adminAuthed` so the unlock prompt comes back. The new-registration toast keys the pending list by `email || id` (`_knownPendingKeys`) — socket ids churn on reconnect and would false-alarm.
- **The admin-unlock input (`#owner-pwd-input`) must stay `type="text"` with `-webkit-text-security`, never `type="password"`.** It lives permanently in the DOM; as a real password field a lingering value made Chrome pop "Save password?" (pairing chat text as the username) on every chat send. `closeOwnerPwd()` also wipes the value on every close — keep both.
- **Admin password reset = clear hash + void all tokens.** `adminResetPassword` sets `password_hash = NULL` and `password_set_at = now()`, then drops live sessions for the email. `resumeSession` rejects any token with `iat < password_set_at`, so whoever held the account is fully signed out and can't auto-resume; the account returns to claimable state (next Join sets a new password). This is also why `password_set_at` exists as a separate column — do not repurpose it.
- **Resume tokens & the reconnection grace period are UX continuity, NOT primary auth.** On approval the server issues an HMAC-signed token (via `SESSION_SECRET`) that the browser replays on load to auto-rejoin (no re-registering/re-approval). "Remember me" picks the storage: checked → `localStorage`, unchecked → `sessionStorage` (saving to one clears the other; `_loadToken` checks localStorage first and sets `_rememberMe` from where it found the token). Tokens die on expiry (`TOKEN_MAX_AGE_MS`) or when `iat < password_set_at`. On disconnect an email-backed player is parked in a ~10s grace window (`GRACE_MS` in `server.js`, keyed by `graceByEmail`) so a refresh/blip resumes the SAME session without their avatar vanishing for others; only after it expires do others see them leave. Tokens are cleared client-side on kick/reject so a revoked user can't auto-resume back in.

### Movement & anti-cheat

- **Server-side rate/movement checks are sanity guards, NOT authoritative simulation.** `server.js` throttles chat/purchase/announcement (token buckets, excess silently dropped — never disconnected) and validates `playerMove` (per-move min interval + map-bounds reject + impossible-jump reject). Two things must stay in sync with the client: (1) movement bounds are derived from `public/assets/Office.tmj` at startup times `RENDER_SCALE`, which MUST equal the client's `setScale(3)`; (2) `MOVE_SPEED` MUST equal the client `SPEED`. Rejections just drop the update (server never rubber-bands the client). The per-move budget is tied closely to walk speed (`MOVE_SPEED · elapsed · MOVE_SPEED_TOLERANCE` + a small `MOVE_JITTER_PX` floor), so a modified client can't chain small hops to move faster than ~walking. The legit ~1-tile seat snap gets its extra `SEAT_SNAP_ALLOWANCE` **only** on a sit↔stand transition (detected via `anim === 'sit'`), cooldown-gated by `SEAT_SNAP_COOLDOWN_MS` so it can't be replayed every frame; out-of-bounds slack is a minimal `MOVE_BOUNDS_EPSILON` (~1 tile), not snap-sized. The FIRST `playerMove` is a bounds-only baseline (the client spawns the avatar at a fixed point that differs from the server's restored coords). Residual: this is not authoritative — a single teleport banked over `MOVE_ELAPSED_CAP_MS` of idling is still possible (bounded to a few tiles); closing that needs authoritative movement (out of scope).
- **Client `COFFEE_MULT` must equal server `COFFEE_MULT` (1.4).** While a coffee boost is live the client walks at `SPEED * COFFEE_MULT` and the server widens its `playerMove` budget by exactly the same multiplier (until `boostUntil` + a 2.5s grace, `BOOST_GRACE_MS`), so boosted steps aren't rejected as speed hacks. Boost/smoke state (`boostUntil`/`smokeUntil`) is in-memory only — a server restart or page refresh mid-boost forfeits the remainder (accepted tradeoff, commented in `server.js`). Usable-item ids (`cigarette`, `coffee`) must match across server `USABLE_ITEMS`, the client `_renderItemBar` list, and the item-bar row ids in the HTML.
- **Outdoor detection assumes the LAST tileset in `Office.tmj` (max `firstgid`, currently `Ext`) is the exterior/grass set.** `server.js` builds an outdoor mask from the Floor layer at startup: a tile is outdoors iff its gid (masked with `0x1FFFFFFF`) belongs to that last tileset, and `isOutdoors(x,y)` samples the player's FEET tile (`(y + BODY_DY=27) / 48`). If a tileset is ever appended after `Ext` or grass gets painted from another tileset, smoking-area detection silently breaks — revisit the mask builder.
- **Work bonus: server `WORK_SEAT_GIDS` {606, 975, 980} must equal the client's desk rule** (gid 606 workstation chairs + the `DESK_FAMILIES` manager chair cells that set `_deskPose`) or the 💼 chip will lie about the +1/min. The server derives the seated tile by inverting the client's seated-sprite placement (`round((x-24)/48)`, `round((y-24+BODY_DY)/48)`) and requires `anim === 'sit'` — a re-imported map with new chair gids silently breaks the bonus. A modified client faking sit at a seat tile earns no more than legitimately AFK-sitting at one of the 100+ chairs, so that farming is accepted (anti-idle out of scope). Daily login bonus (+10) is granted at the end of `restorePlayer` by one atomic conditional UPDATE on `jpo_players.last_daily_bonus` (a `date`, compared to DB `CURRENT_DATE` = UTC day boundary — accepted); session-only (no-email) players never get it.

### Map, furniture & office objects

- **Server `OBJECTS` and client `OFFICE_OBJECTS` must stay in lockstep** (ids, x/y anchors in scaled world px = tile*48, and radii). The client only renders prompts/highlights and sends an `interact {object}` intent; the server re-checks proximity against ITS copy, so drift makes an object visibly promptable but unusable (or vice versa). The water cooler's visible sprite is NOT a map tile — it's a custom client-only image (`public/assets/water_cooler_16x32.png`, drawn in `create()` as two cropped halves so the top occludes players on the row behind, plus a static collision zone on its base tile). If the cooler's anchor ever moves, the sprite/zone coords in `create()` and the `hl` box must move with it; the server knows nothing about the sprite or its collision (movement validation doesn't check tiles). The arcade path reuses `startRpsChallenge` — the same helper as direct challenges — so every existing RPS cleanup seam (`cancelMatchFor` on disconnect/kick/dropLive) applies to arcade matches automatically; don't fork a separate arcade match flow. Object cooldowns (`coffeeMachineReadyAt`/`waterReadyAt`/`fridgeReadyAt`) are keyed by email (fallback socket id) and in-memory only — a restart forgives them by design. The Pantry fridge tiles (GIDs 682–717) were removed from the client `BOARD_GIDS` set so the fridge is an interactive object, not an announcement board — the Pantry deliberately has NO board now; if a real board is ever added there, use different tiles, and never add furniture GIDs to `BOARD_GIDS` without checking what else on the map uses them.
- **Furniture tiles are solid by default; only explicit seat/aisle openings are walkable.** Both the Wall and Furniture tile layers collide by exclusion (`setCollisionByExclusion([-1])` — every non-empty tile blocks movement), and only known chair cells (`isFurnSeat`, `DESK_FAMILIES`) get their collision explicitly cleared. **When adding or moving furniture in `Office.tmj`, always check the tile(s) directly below/around it for existing open corridors** — a multi-tile object dropped across a walkway will silently seal it off (this happened once with a new IT/Dev desk; fixed by opening a bypass gap in the adjacent wall rather than shrinking the desk, since a real desk needs its full seat + legs). Prefer verifying the affected rows/columns of the Wall and Furniture layers before and after any tilemap edit.
- **`CLOTH_MAX` in `server.js` must equal `CLOTH_COLORS.length - 1` in `public/index.html`.** It clamps shirt/pants colour indexes; if the client palette grows, bump this or valid choices get rejected.

### Office After Dark rounds

- **The round engine follows the same double-settle discipline as `finishMatch`:** `endRound` flips `round.state = 'ending'` SYNCHRONOUSLY before any await, and every other mutator (`roundKill`, `roundHandleLeave`, the end timer, `checkKillerWin`) re-checks `state === 'active'` first — keep that ordering when touching payout or leave logic. Round⇄duel mutual exclusion is symmetric and relies on `startRpsChallenge` registering BOTH sockets in `rpsBySocket` at pending time: `roundStart`/`roundJoin` reject anyone in `rpsBySocket`, and `rpsChallenge`/arcade reject anyone in `round.members` — `rpsRespond` deliberately has no `inRound` check because the pending registration makes it unreachable mid-round; don't "fix" that.
- **Killer identity is secret until `roundEnd`.** Role goes per-socket in `roundBegin` only; the shared roster carries `{id, name, alive}` and nothing else; `roundKilled` names the victim only; non-killer `roundKill` probes are dropped SILENTLY (an error reply would confirm who the killer is). Keep any new round event to this rule.
- **`roundHandleLeave` is hooked into the same three seams as `cancelMatchFor`** (disconnect, `kickPlayer`, `dropLiveByEmail`) and is keyed off `round.members`, not `players[]`. Client-side, `_roundReset()` is the single teardown (roundEnd/roundCancelled/socket disconnect/kicked) so nobody can be stranded in the dark. The darkness overlay is ONE oversized fixed div with a static radial gradient, repositioned per frame via transform from the scene's `update()` (`window._roundFrame`) — valid because the game runs `Phaser.Scale.RESIZE` (1 game px = 1 CSS px at zoom 1); if the scale mode ever changes, that math breaks.
- **`ROUND_JOIN_MS` / `ROUND_DURATION_MS` env overrides are TEST KNOBS ONLY** (headless tests can't wait 3 real minutes); never set them in production. Kill cooldown/range/prize/min-players are fixed constants shared with the client via the `roundBegin` payload, so the client never hardcodes stale values.

### Cosmetics, shop & wardrobe

- **Emote ids in the server `EMOTES` allowlist must match the client `EMOTES` array in `public/index.html`.** The client maps ids to emoji; unknown ids are silently dropped on both sides. Number keys 1–8 map to the client array order. Emote bubbles intentionally reuse the chat-bubble slot (`localBubble` / `entry.chatBubble`) so all existing follow-the-player positioning works unchanged — an emote replaces a showing chat bubble and vice versa.
- **Client and server `DEPARTMENTS` lists must stay identical (values AND order).** The server allowlists at both write paths (`register` → invalid becomes `''`; `setDepartment` → silent drop), so the DB only ever holds one of the fixed strings or `''` — that's why the profile card and admin Dept cell can render them safely. "Set once" applies only to the `setDepartment` path (atomic `WHERE department=''`); the register upsert's CASE guard only stops an EMPTY incoming department from wiping a set one — a re-register via Join with a different dropdown pick DOES overwrite it (same accepted re-register profile seam as wardrobe colours). The profile card is non-blocking by design (no mutual-exclusion seams, no Esc handling — close is button/outside-click only), sits at z-index 8400 below the rps modals (8500) so incoming challenges stay on top, and renders server data with `textContent` only. `getProfile`/`setDepartment` share one `profileBucket`; profile lookups are by live socket id (like whispers), reading the in-memory state.
- **Wardrobe (paid outfit change) seams.** Server `changeOutfit` REJECTS out-of-range/non-integer indexes with a silent drop (deliberately NOT clamped — an invalid intent is discarded like other forged payloads); the buyer gets `outfitSuccess` + `coinUpdate`, everyone else re-renders from `playerOutfitUpdate` (client skips self). Re-rendering leans on the 50ms `playerMove` stream: `_applyRemoteOutfit` only swaps `entry.texKey` and `_applyLocalOutfit` only calls `setTexture` when standing-idle — every other pose (walk/sit/desk-stand, local and remote) re-derives from `playerTexKey`/`entry.texKey` each tick, so don't add explicit re-posing. The 25-coin price appears in TWO client places (the `WARDROBE_PRICE` JS const and the hardcoded shop sub-text) but both are display-only — the server's `WARDROBE_PRICE` is authoritative. The wardrobe's live preview (`_redrawWardrobePreview`) reuses the registration preview's recolor pipeline (`_charImages`/`_charZoneColors`/`_applySwaps`) with the PENDING swatch picks over the player's real character/hair/skin — it's pure client rendering, refreshed from `_renderWardrobe`, and never touches the Phaser textures until the server confirms the purchase. Accepted residual: re-registering via Join re-applies the form's free colour picks over a bought outfit (pre-existing profile-update seam; sign-in, refresh, and resume-token paths all keep bought colours).
- **Server `SHOP` ids/prices and the client `COSMETICS` catalog must stay in lockstep.** The server is authoritative (rejects unknown ids, enforces the real price), so drift only breaks UI (a row that can't be bought or a wrong price label). Rendering is driven ONLY by the `equipped` field (`jpo_players.equipped_cosmetic`, '' = none — one worn item at a time, emoji overlay above the head); the owned `cosmetics` array renders nothing. Buying auto-equips in the same atomic UPDATE as the coin spend; `equipCosmetic` (free switch/take-off) enforces ownership inside its UPDATE's WHERE clause and is deliberately NOT blocked mid-match (no coins move — only `buyCosmetic` keeps the `rpsBySocket` block that protects the wager invariant). Throttled/no-op equips are silently dropped (shares `buyBucket`).
- **Sprite wearables (`shades`/`cap`/`chain`) are a client-side rendering branch, not a new server concept.** The server treats them as ordinary SHOP cosmetics; the client's `WEARABLE_DEFS` map decides which cosmetic ids render as pixel-art overlay sprites (`public/assets/wear_*.png`, preloaded in Phaser) — any equipped id NOT in `WEARABLE_DEFS` falls back to the old emoji-text path (`_makeCosmetic` branches; both local and remote players share it). A new sprite wearable needs FOUR things in lockstep: server `SHOP` entry, client `COSMETICS` row, `WEARABLE_DEFS` entry, and a preloaded PNG (missing PNG = invisible item). The PNGs are TWO-frame spritesheets — frame 0 = front view (facing down), frame 1 = side profile drawn facing RIGHT (`_placeWearable` picks the frame from facing and `flipX`s for left, plus a `side` x-nudge; facing up hides the wearable entirely) — a single-frame PNG will silently render garbage because the loader slices it at the declared frameWidth. Placement gotcha: every `dy` (and optional `sideDy` for the side frame) is EMPIRICAL — each wearable's art sits differently inside its texture frame, so the head-geometry estimate (head top ≈ y−24, eyes ≈ y−12, chin ≈ y0) is only a starting point; always sweep candidate values live (mutate `_gameScene.localCosmeticDef` from the console/puppeteer) and verify with in-game screenshots in all three visible facings. The chat-bubble extra lift applies ONLY to emoji cosmetics (`localCosmeticDef`/`cosmeticDef` null checks) — sprite wearables don't raise bubbles.
- **Client `USABLES` catalog ↔ server `USABLE_ITEMS` lockstep** (ids incl. the group items `coffee_round`/`confetti`/`fireworks`/`pizza_party`; client costs/labels are display-only — the server enforces real prices and charges). Group use: the server computes `nearbyIds(GROUP_RADIUS)` (420 scaled px ≈ 9 tiles) from LIVE positions at the moment of use, decrements the charge with the same atomic conditional jsonb UPDATE as single-use items, then emits one `coffeeBoost {id,durationMs,mult,emoji}` per boosted recipient (coffee round = `COFFEE_MS` 45s, pizza = `PIZZA_MS` 90s — both use the one `COFFEE_MULT` because the move-budget widening only knows one multiplier) plus one `groupEffect {effect,x,y}` visual for everyone. `boostUntil` max-extends, so a coffee round can never SHORTEN a running pizza boost. Effect gates run before the charge decrement, so a rejected use never burns a charge.
- **Pets: server `PETS` catalog ↔ client `PETS` catalog must stay in lockstep** (ids/prices; server authoritative, drift only breaks UI — same contract as SHOP/COSMETICS). Pet ids all carry the `pet_` prefix ON PURPOSE: owned pets live in the SAME `jpo_players.cosmetics` array as wearables, and the prefix keeps the two id spaces disjoint (`buyCosmetic` rejects `pet_*` ids and `buyPet` rejects non-`pet_*` ids — keep both guards). The active pet is a SEPARATE slot (`jpo_players.equipped_pet`, '' = none) so a pet and a worn cosmetic render simultaneously; `buyPet`/`equipPet` mirror `buyCosmetic`/`equipCosmetic` exactly (shared `buyBucket`, atomic coin UPDATE, ownership in the WHERE clause, mid-match block on buy only). Pet MOTION is never networked: each client derives its pets' positions locally every frame from the owner's sprite (trailing at `PET_GAP` px behind the last movement direction), so `playerMove` traffic is unchanged — only equip/unequip events (`playerPetUpdate`) cross the wire. `shopTab()`/`_refreshShopUI` toggle three hardcoded tab panes (Wearables = `COSMETICS`, Items = `USABLES`, Wardrobe) and paginate at `SHOP_PAGE_SIZE` (6) with `_shopTab`/`_shopPage` state (tab switch resets to page 1). The server knows nothing about tabs — adding a catalog entry lands on the right tab automatically; adding a NEW tab means touching the `#shop-tabs` buttons, the pane toggling, and the pager catalog pick in `_refreshShopUI`.

### Mini-games (RPS / Tic-Tac-Toe / Quick Draw / Icebreakers / Word Race / Trivia Duel / Connect Four)

- **ALL mini-game matches live only in `rpsBySocket` (both socket ids map to the same match object); every cleanup seam keys off it.** The match object carries a `game` field (`'rps'|'ttt'|'qd'|'ib'|'wr'|'trivia'|'c4'`, server `GAMES` allowlist) but there is ONE lifecycle: `disconnect`, `kickPlayer`, and `dropLiveByEmail` all run `cancelMatchFor` — a mid-match disconnect cancels immediately with no coins moved (the reconnection grace window does NOT keep a match alive), while a match already in `settling` is never cancelled. Accepted tradeoff: because ttt is full-information, a player about to lose a wagered ttt game can disconnect to void the match (documented, not exploitable for gain — no coins ever move on cancel). First pick locks (repeat `rpsPick`s are ignored); pick-phase timeout: exactly one picked → forfeit win for the picker, none picked → cancelled; ttt move timeout → forfeit loss for the stalled player; qd tap before the signal → instant loss. `buyCosmetic` is rejected while in `rpsBySocket` — that keeps the accept-time balance check sufficient, because the coin tick only ever ADDS coins and the shop is the only other spend. Settlement (`rpsSettle`) is SQL-first for all four email/session player combos (a single CTE with a `coins >= wager` guard when both are email-backed); in-memory coins are only updated from `RETURNING` values, and the wager is re-verified at accept time (challenge-time balance checks are advisory UX only). The challenge rate bucket is checked before ALL validation, so even rejected challenges consume a token.
- **Every game-over path MUST route through `finishMatch` in `server.js`, which flips `m.state = 'settling'` SYNCHRONOUSLY before its first `await`.** That synchronous flip is the only thing preventing `cancelMatchFor` (disconnect/kick) from cancelling a match whose settlement SQL is already in flight — an async gap between "decided" and "settling" would let a sore loser disconnect-race the wager transfer. Win/draw/forfeit/timeout/early-fire in all seven games call it; never settle inline in a handler.
- **Icebreakers/Word Race seams.** The multi-round ib flow adds `roundTimer`/`revealTimer` to the match object — both are in `clearMatchTimers`, and every timer callback captures its round number and re-checks `state`/`game`/round at fire time, so a stale timer from a settled or advanced match is always a no-op (keep that pattern for any future round-based game). `ibExtras` returns a `(me, them)` closure because `finishMatch` calls `extras(recipientId, otherId)` — a single-arg extras (like wr's) is fine, but per-recipient scores need both. `IB_PROMPTS` and `WR_WORDS` are server-only content — prompts/scrambles travel in events, so growing either pool needs NO client change (unlike EMOTES/SHOP/etc.). The wr answer word NEVER leaves the server before game over (`wrSubmit` compares server-side; wrong guess = private `wrWrong`, throttled by `wrBucket` checked before the compare); `wrScramble` retries until the scramble differs from the word and isn't itself a pool word. The wr text input stops key propagation and toggles Phaser's global key capture on focus/blur (same pattern as the owner-password input) — `rpsResult` and `closeAllRps` both blur it, so a cancelled match can't leave the keyboard captured. ib has no submit bucket by design: the first `ibSubmit` locks (`m.ibSubs`), so spam is O(1) no-ops.
- **Trivia Duel / Connect Four reuse the existing timer + settle seams — keep it that way.** Trivia uses `roundTimer`/`revealTimer` (ib's pattern: every timer callback captures its round and re-checks `state`/`game`/round at fire time); c4 uses `moveTimer` (ttt's pattern) — all three are cleared by `clearMatchTimers`, so `cancelMatchFor`/`finishMatch` clean both games with no new code. `TRIV_QS` is server-only content like `IB_PROMPTS`/`WR_WORDS` (questions travel in events; `TRIV_ROUNDS` DISTINCT questions are drawn at accept time so a match never repeats one) — growing the pool needs no client change. The correct answer index never leaves the server before the reveal. C4's board is a flat `C4_COLS*C4_ROWS` array; `c4Drop` validates the column with `Number.isInteger` + range and gates on `m.turn`, `trivAnswer` locks on first answer — that turn/lock gating is WHY neither event needs its own rate bucket (spam = O(1) no-ops before any work). Both route every game-over through `finishMatch` like the other five games.
- **New games reuse the `rps*` socket event names on purpose** (`rpsChallenge` carries `game`, `rpsStart` branches the UI, one `rpsResult` renders all verdicts; only the in-game intents are new: `tttMove`, `qdTap`, `ibSubmit`, `wrSubmit`, `trivAnswer`, `c4Drop`). Client `GAME_META` and server `GAMES` must stay in lockstep — the server rejects unknown games with "Unknown game." and the client falls back to rps metadata, so drift degrades gracefully but still means a picker entry that can't start. Client `CHALLENGE_RANGE_PX` (⚔️ quick-challenge button) must equal server `RPS_RANGE_PX` (480) or the button will offer targets the server then rejects as out of range. The arcade path passes the picked `game` through `interact {object:'arcade', game}` into the same `startRpsChallenge` — arcade matches are always friendly (0-wager) and the client hides the wager fields in arcade mode.

### Sprites & rendering

- **Seated poses reuse Adam's geometry for every character.** All non-Adam seated sheets (`{Alex,Amelia,Bob}_sit/sit2/sit3_16x16.png`) are recolours of Adam's seated sheets, so their pixel layout is identical. `_sitZones` (in `public/index.html`) retunes only the Y-bands per direction (`SIT_ANATOMY`, values = the generator's HAIRMAX: right/down hair→y22, up→y17). Regenerating these PNGs must keep HAIRMAX in lockstep with `SIT_ANATOMY`.
- **Seated shirt/pants zones MUST keep `yMin = hairYMax` (do not "optimise" it away).** It is tempting to drop the Y gate for a character whose nominal shirt colour looks far from its hair colour — do NOT. Each zone is a multi-shade family, and a character's darker hair shades can fall inside the shirt threshold (e.g. Alex). Customizing the shirt while leaving hair at default SKIPS the hair pass, so without the gate the un-swapped hair mass gets repainted in the shirt colour. The gate costs only a ~2px shoulder seam (accepted for all seated chars). See the long comment above `_sitZones`.
- **Amelia's seated hair is short (Adam's shape), not her long standing hair.** Accepted scope tradeoff — the seated sheets inherit Adam's silhouette, so her flowing hair does not appear while sitting.

### Ops & tooling

- **Don't add a build step to jpo-huddle.** The client is CDN-loaded plain JS and the server is plain ESM by design; `node server.js` must keep working.
- **Load-test metrics are opt-in and must stay zero-cost when off.** `LOADTEST_METRICS=1` enables the `[metrics]` log line (event-loop lag, RSS, coin-tick ms, `mv_ok/mv_thr/mv_rej` move counters) — every counter increment in hot paths is gated on the `LT_METRICS` flag; keep it that way. When reading load-test results, judge move delivery against ACCEPTED moves: the 33ms move throttle drops TCP-bunched 50ms-cadence sends by design (~15% at 100 players), so raw delivery ratio understates health. Coin tick at 100 DB-backed players takes ~1.3s wall (sequential UPDATEs) but is async and doesn't block the loop; batch it only if the team grows well past 100 concurrent.
